Pulse Local Quick Start

One make target builds a kind cluster, the operator, a small shop to monitor, and a canary of every type Pulse supports. Ten narrated scenarios then exercise every synthetic shape and intelligence trigger. The narrated tour prints the live evidence at every stage, so this is a system walkthrough rather than a pass/fail smoke test.

Before you start

Everything runs locally. The demo never calls out to Slack, Datadog or an LLM provider — a small sink pod stands in for all three and records what it was sent, so you can read the real payloads back with kubectl logs.

needwhy
kindCreates the single-node cluster from hack/demo/kind.yaml.
kubectlEverything the Makefile and the scenario script do.
podman or dockerBuilds the operator images and one deterministic demo-target image. Pass CONTAINER_TOOL=podman if you use podman.
python3make fetch-models downloads and converts the two models. Standard library only.
go 1.26+Generating manifests. kustomize and friends are downloaded into bin/ for you.

Budget roughly 4 GB of RAM and 6 GB of disk for the cluster and images. The converted model artifacts baked into the images are roughly 210 MiB; downloads and conversion cache can bring hack/models/ to roughly 335 MB. It is gitignored and reused.

Bring it up

One command does all five steps below. They are broken out so you can see what it did, and so you can re-run any single one after a change.

# podman users: add CONTAINER_TOOL=podman to every make command on this page
make demo-up

Every demo command explicitly targets kind-pulse-demo; it does not change or trust your current kubeconfig context. Use DEMO_CLUSTER=my-name consistently to choose another dedicated Kind cluster. Startup is ordered even when Make is invoked with parallel jobs.

Create the cluster

A single-node kind cluster called pulse-demo. If it already exists this is a no-op, so the whole quick start is safe to re-run.

make demo-cluster

Build the images and load them into kind

Four images: three Pulse components plus the deterministic demo target. The probe runner stays CGO_ENABLED=0 on distroless/static with the static potion model baked in; only the incident engine carries ONNX Runtime and MiniLM.

make demo-images

Install the CRDs

Three kinds: HttpCanary, GrpcCanary, and the AnomalyPolicy that carries every model, trigger and action setting.

make demo-install

Deploy the operator

The controller lands in pulse-system. It creates the probe-runner StatefulSet itself, and creates the incident engine only once some canary opts into a policy — a cluster that never uses this feature never gets the extra pod.

make demo-deploy

Deploy the shop, the sink, the policy and the canaries

Six target deployments in namespace shop, the recording sink in pulse-demo, one AnomalyPolicy, and ten canaries.

make demo-workloads

The target waits for every deployment and canary to become ready before it returns. Start with the system view: it explains the data path, resolved models, action order, live validations and active-versus-proposed topology using reads from the running cluster.

make demo-explain

What is being monitored

One canary per shape Pulse supports, so the demo doubles as a worked example of every field. All ten opt into the same policy with the same two-line block; delete that block from any of them and it goes straight back to being an ordinary pass/fail check.

canarykindwhat it exercisestarget
catalogueHttpCanary Status code plus a containsText body assertion. The drift baseline is built here. demo-target Go service
checkoutHttpCanary A declared downstream of catalogue in spec.topology. real catalogue caller
searchHttpCanary The second declared downstream — two dependents prove the incident is collapsed, not paired. real catalogue caller
no-contentHttpCanary A non-200 expectation (expectedStatus: 204). demo-target Go service
login-journeyHttpCanary A two-step scripted journey sharing one client and cookie jar across steps. demo-target Go service
mcp-toolsHttpCanary A real MCP handshake: initialize, notifications/initialized, tools/list, then asserts health.check is offered. demo-target Go service
ordersGrpcCanary Standard grpc.health.v1 health checking. demo-target Go service
similar-a / similar-bHttpCanary An identical failure pair with no declared edge, used to prove model-only similarity correlation. independent Go service
unrelatedHttpCanary A healthy control that is failed alongside the outage with a distinct content-contract error. independent Go service

The opt-in is exactly this, on every one of them:

  # hack/demo/20-canaries.yaml
  intelligence:
    policyRef: {name: demo-triage, namespace: pulse-system}
What the demo policy turns on

All four triggers, both declared dependency edges, and all four action types pointed at the local sink. Demo overrides are explicit: drift warmup is 5 instead of 20, latency warmup is 8 instead of 30, novelty uses 0.999 and 1 second instead of 0.80 and 300 seconds, and throttling is 0/50 instead of 900/4. These shorten isolated chapters; the primary drift, latency and correlation thresholds retain their defaults.

# hack/demo/10-policy.yaml, abridged
spec:
  triggers:
    bodyDrift:          {enabled: true, threshold: "0.15", warmupChecks: 5, consecutiveBreaches: 2}
    latencyShift:       {enabled: true, zScoreThreshold: "3.0", warmupChecks: 8}
    failureCorrelation: {enabled: true, windowSeconds: 120, similarityThreshold: "0.85"}
    failureNovelty:     {enabled: true, clusterThreshold: "0.999", settlingPeriodSeconds: 1}
  topology:
    dependsOn:
      - {canary: shop/checkout, upstream: [shop/catalogue]}
      - {canary: shop/search,   upstream: [shop/catalogue]}
    inferDependencies: true
  actions:
    - {name: local,       type: metric}          # Prometheus incident counter
    - {name: investigate, type: llm}             # one call per incident, not per canary
    - {name: notify,      type: slack}           # reads the investigation the llm action wrote
    - {name: ship-logs,   type: observability}   # provider: datadog
  # Keep local scenario replays deterministic; production policies normally use a cooldown.
  throttle: {cooldownSeconds: 0, maxPerHour: 50}

Keep the evidence layers separate: protocol assertions decide pass/fail; Potion compares passing HTTP bodies; EWMA statistics detect latency without a model; MiniLM compares failure text or clusters replay novelty. Declared topology can merge an incident without MiniLM. Graph/onset ranking chooses the root cause; the deterministic local LLM fixture only writes a human-readable investigation after that decision. A zero score is meaningful only when the live detector state says ready.

Make it fire

Ten scenarios cover every canary shape and both intelligence tiers. Each command first explains the validation, mutation and internal path, then prints the live probe result, model decision, incident graph and newly dispatched payloads. Assertions still stop the run if that evidence contradicts the explanation.

# the complete narrated walkthrough
make demo-tour
make demo-tour-paced     # pause with each failure live so you can inspect it

# demo-scenarios is an equivalent alias; run individual chapters below
make demo-green-deploy   # semantic body drift while status remains 200
make demo-latency        # three local baselines catch one delay propagating through real callers
make demo-http-contract  # expected 204 changes to 200
make demo-content        # status stays 200 but a required body marker disappears
make demo-journey        # second journey step violates its assertion
make demo-mcp            # tools/list loses health.check
make demo-grpc           # grpc.health.v1 reports NOT_SERVING
make demo-outage         # one upstream failure creates two real downstream failures
make demo-similarity     # MiniLM-only merge with no declared topology
make demo-novelty        # repeat shape reports novel=false and skips the LLM

A passing release that is wrong

potion · hot path

Switches the demo target's behavior in place to simulate a new release while it still answers 200 with well-formed JSON — but the collection comes back empty. The in-place control avoids introducing rollout connection errors, so the evidence is only the failure being taught: a bad feature flag, a query regression, or an index that never finished rebuilding.

make demo-green-deploy

Expect: catalogue stays Healthy while status.intelligence.trigger becomes bodyDrift. No status code and no containsText assertion catches this, because nothing about the response is malformed — only its meaning changed.

A correlated outage

MiniLM · cold path

Breaks the catalogue. checkout and search read from it, so three canaries go red within one window. The script simultaneously gives unrelated a different content-contract failure as a negative control.

make demo-outage

Expect: one incident spanning three canaries, with catalogue as rootCause and the other two downstream; one LLM investigation and one Slack message, not three. The merge reason is the declared dependency edge; this chapter does not claim MiniLM was necessary. And unrelated in an incident of its own — simultaneity alone is not treated as evidence.

A model-only merge

MiniLM · cold path

Breaks similar-a and similar-b with the same assertion failure. They have no declared dependency. A simultaneous, dissimilar gRPC failure is the negative control.

make demo-similarity

Expect: the pair shares one incident whose mergeEvidence records measured similarity and threshold; the gRPC control has a different incident ID.

A failure you have seen before

MiniLM · cold path

Restores the catalogue, then breaks it again the same way. The failure text clusters with what the engine already saw.

make demo-novelty

Expect: the incident opens again, but the second occurrence does not earn a fresh investigation. Slack and observability still receive one record for the new incident; novelty gates only the expensive LLM step.

Put everything back whenever you want:

make demo-restore

Restore returns every target—including the negative control—to Healthy and waits until every incident is closed.

What the actions actually sent

The sink logs every request it receives, up to a documented 64 KiB body limit with explicit truncation metadata. This renders every matching LLM prompt, plain-Markdown Slack message, and Datadog log entry that was really posted. The LLM response is deterministic and labels itself as simulated; no external inference occurs. Credential values are never printed.

make demo-show

The investigation, on the canary itself

The llm action writes its markdown root-cause analysis straight back into the root cause's status, so it is on the object you were already looking at.

kubectl --context kind-pulse-demo -n shop get httpcanary catalogue \
  -o jsonpath='{.status.intelligence.investigation}'

Kubernetes Events are recorded too, on the canaries themselves:

make demo-events

Validation lab

The end of the tour is the beginning of the useful part: change a contract, observe the same surfaces Pulse uses, then restore it. The lab maps every validation to its configuration field, worked canary and narrated scenario.

make demo-lab                         # list every validation surface
make demo-lab VALIDATION=mcp          # inspect the live MCP spec and status
make demo-validate VALIDATION=mcp     # run that narrated experiment
make demo-inspect CANARY=mcp-tools    # desired spec + observed status

To create a validation failure without changing the demo application, change the canary's assertion itself. This example asks for a body marker the catalogue does not return:

kubectl --context kind-pulse-demo -n shop patch httpcanary unrelated --type merge \
  -p '{"spec":{"containsText":"a-marker-that-is-not-present"}}'

# status is asynchronous; wait until this exact new assertion has been evaluated
until kubectl --context kind-pulse-demo -n shop get httpcanary unrelated \
  -o jsonpath='{.status.message}' | grep -q 'a-marker-that-is-not-present'; do sleep 1; done

make demo-inspect CANARY=unrelated
make demo-incidents

# recreate only the demo-owned definitions, then restore behavior
make demo-reset-definitions
make demo-restore

The same loop applies to expectedStatus, each journey[] step, mcp.requiredTools, the gRPC service, per-canary drift/latency overrides, policy correlation thresholds and novelty clustering.

curl -s localhost:9090/metrics | grep drift_score

Inferred edges are proposals only. They appear in policy status for a human to promote into spec.topology.dependsOn; nothing merges an incident on an inferred edge alone.

When the evidence does not appear

symptomwhat to verify
Wrong or missing clusterRun kubectl --context kind-pulse-demo cluster-info, or pass the same DEMO_CLUSTER to every Make target.
Image pull or rollout stallsInspect pods and events in pulse-system and shop; rerun make demo-images demo-deploy demo-workloads.
No result / stale resultmake demo-status marks missing and older-than-45-second live results. Do not interpret missing as a zero score.
Detector says warmingWait for the configured number of normal, interval-paced checks. There is no startup burst; do not restart a runner while the target is broken.
No LLM requestInspect novel, settling, cooldown, and hourly rate limits. A known incident intentionally skips LLM but still sends Slack and observability actions.
Viewer warns about truncationThe sink received more than 64 KiB. The warning includes the original byte count; use a smaller bounded demo payload.
An interrupted tour left failures liveRun make demo-restore. If definitions were edited, run make demo-reset-definitions first.

Tear it down

make demo-down

Deletes the kind cluster and nothing else. The downloaded models stay in hack/models/ so the next make demo-up skips the download.

The design behind all of this — why there are two models, what a cosine distance actually measures, and how the drift score is computed — is in the model intelligence guide.
