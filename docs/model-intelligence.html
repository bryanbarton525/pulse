Pulse / operator guide

Model intelligence in Pulse

What actually got built, how to run it, and why one model lives inside the probe runner while the other lives somewhere else entirely. The short version of that last part: where the text becomes a vector decides what leaves the pod.

What it does

Pulse was a pass/fail synthetic monitor. A canary declared expectedStatus: 200, the runner checked it, and the CR got Healthy or Unhealthy. Nothing else happened — no notification, no correlation, no history.

This adds an opt-in layer that reads the check results with embedded models. It is genuinely optional: a canary with no spec.intelligence behaves exactly as before, and a cluster with no AnomalyPolicy deploys no extra pods.

Why it does not "detect anomalous failures"

This is worth understanding before anything else, because it shapes every design decision below.

A canary's failure is deterministic by construction. It fails when your assertion says it should. The runner builds those failure messages from a handful of format strings, so once volatile tokens are masked away, Expected 200 but got 503 and Expected 200 but got 502 are the same string. Scoring them with a 384-dimensional model to decide whether they are "unusual" is a switch statement in an expensive costume.

The signal is in two places your assertions cannot reach:

  • The response body, which the runner used to read and immediately throw away.
  • The relationships between concurrent failures, which nothing tracked at all.

The model watches the checks your assertions say are fine.

Four triggers

None of them claim a deterministic result is anomalous. Each asks a question the assertion cannot answer.

TriggerQuestionFires onPath
bodyDrift The check passed — did the body's meaning change anyway? every passing check hot
latencyShift Green, but getting slower? every check hot
failureCorrelation Is this one incident or five? Which is the root cause? failures only cold
failureNovelty Have we seen this failure shape before? failures only cold

The first two catch green-but-wrong: an emptied result set, a stack trace inside a 200, a maintenance page served with the right status code, a p99 creeping upward. You cannot pre-write an assertion for these because you do not know in advance what wrong will look like.

The last two do triage: collapse a storm into one incident with one investigation, and keep the four-hundredth repeat of a known failure quiet.

Correlation merges on evidence, never on timing

Two canaries failing at the same moment is not evidence of anything — in a cluster of a few thousand checks, unrelated things fail together constantly. A merge requires an actual reason:

  1. a declared dependency in spec.topology.dependsOn, or
  2. failure text showing both checks hit the same wall — two canaries with no declared relationship both reporting an identical dial timeout are telling you they share an upstream nobody wrote down.

Because the gate is evidence rather than configuration, correlation works across canaries governed by different policies. That matters: policies follow team ownership, but outages follow infrastructure, and your payments canary and its database canary are rarely owned by the same team.

Pulse also learns dependency edges from co-occurrence, but only ever proposes them in AnomalyPolicy.status.inferredDependencies. A proposal never affects merging until you copy it into dependsOn yourself. Co-occurrence is not causation, and an edge that silently redirected blame would send someone to debug the wrong service at 3am.

How the math works

Everything above rests on one operation, applied three different ways. It is worth building up from nothing, because once the operation is clear the thresholds stop looking arbitrary.

What the drift score is actually for

Start with the problem, because the arithmetic only makes sense against it.

An assertion can only check for something you thought of in advance. expectedStatus: 200 catches the endpoint being down. containsText: "widget" catches that one string disappearing. Neither catches the response that is structurally fine and semantically wrong — the list that silently went empty, the JSON that became an HTML error page, the object that started returning a stack trace with a 200 on it. You cannot write an assertion for a failure mode you have not imagined yet.

The drift score replaces "does this match what I predicted?" with a different question: "does this look like what this endpoint has been returning?" That question needs no prediction, because the endpoint's own recent history supplies the answer.

So the score is a single number answering: how far has this response moved from normal for this probe? Its job is to be near zero for a healthy endpoint that is merely varying, and to climb sharply when the meaning of the payload changes — with enough separation between those two states that a fixed threshold can tell them apart.

A green check with a rising drift score is the case that motivates all of this.

Step one: text becomes numbers

A model cannot compare two strings for meaning — strings.Contains is the best you get. So the first move is to turn text into a list of numbers, chosen so that texts meaning similar things get similar lists. That list is called an embedding or a vector.

For potion, the hot-path model, the whole process is genuinely this small:

The individual numbers mean nothing on their own. Dimension 237 is not "database-ness". Meaning is spread across all 512 together, and only relationships between whole vectors are interpretable. This is why you never inspect a vector — you only ever compare two.

Step two: comparing two vectors

Think of a vector as an arrow from the origin. Two documents about the same thing produce arrows pointing in nearly the same direction. Documents about different things point elsewhere.

Direction is what we want, not length. A response with 2 items and one with 40 items should count as similar if they are structurally the same thing — so the measure has to ignore how "big" the vector is and look only at the angle between them. That measure is cosine similarity.

Here it is on two-dimensional vectors, small enough to check by hand:

# two vectors A = (3, 4) B = (4, 3) # scale each to length 1 (length = √(3² + 4²) = 5) Â = (0.6, 0.8) B̂ = (0.8, 0.6) # cosine similarity = multiply pairwise, then add similarity = (0.6 × 0.8) + (0.8 × 0.6) = 0.48 + 0.48 = 0.96 # → an angle of about 16° # distance is just the flip side distance = 1 − 0.96 = 0.04

Two things fall out of that arithmetic, and both matter downstream:

  • Scaling to length 1 first ("normalising") is what lets the comparison be a plain multiply-and-add. It also means averaging vectors later stays well behaved.
  • Similarity and distance are the same number, inverted. distance = 1 − similarity. Pulse uses both, which is a real source of confusion — see the table at the end of this section.

The range, and what it feels like

Similarity runs from 1 (identical direction) through 0 (perpendicular, unrelated) to −1 (opposite). Distance therefore runs 0 → 1 → 2. For real text you almost never see the negative half, so in practice the useful ruler is 0 to 1 — and these are Pulse's own measured numbers, not illustrations:

0.000byte-identical text after masking — the cache-hit case
0.015median healthy check against its baseline
0.063worst healthy check observed over 300 samples
0.150← the default drift threshold sits here
0.200the result set went empty
0.473a stack trace where JSON used to be
0.591an HTML maintenance page
1.000perpendicular — nothing in common

The gap between 0.063 and 0.200 is the entire safety margin. That is why the threshold had to be measured rather than guessed: it is not a property of the model, it is a property of how much your payloads normally vary.

Step three: what "the baseline" actually is

Drift compares a body against that probe's own history. But "history" is not a stored list of past bodies — it is a single vector, the running average of every healthy body seen so far. Averaging vectors is exactly what it sounds like: average each of the 512 positions independently, then rescale to length 1.

The average of a set of arrows points in their "middle" direction, so the baseline ends up pointing the way a normal response for that endpoint points. At about 1.5 KB per probe, thousands of probes cost a few megabytes.

It is not a plain average, though — it is exponentially weighted, so recent checks count for more:

# α (alpha) controls how fast the baseline moves α = max( 1/samples , 1/warmupChecks ) # with warmupChecks = 20: sample 1..20 → α = 1/n # a true running average sample 21+ → α = 0.05 # floors here — a rolling 20-sample memory # then, for each of the 512 positions: baseline = baseline × (1 − α) + new × α # and rescale the result to length 1

The floor is the interesting part. Without it, α keeps shrinking and after ten thousand checks the baseline is frozen — a legitimate deploy that adds a field would alert forever. With it, the baseline keeps a rolling memory and gradually accepts genuine change while still reacting to sudden change.

Two rules that keep it honest

Only passing checks update it

A failing check usually returns an error page. Averaging that in would drag the baseline toward "broken" and quietly redefine normal.

Drifted checks are not absorbed

Once a body is over the threshold it is scored but not averaged in. Otherwise a sustained outage trains itself into the baseline and the alert fades out exactly when it matters.

Step four: warmup, and why it exists

An average of two samples is noise. Until warmupChecks samples have been absorbed, the baseline is being built and scoring is suppressed entirely — Warming is returned instead of a score, and nothing can fire. At the default of 20 checks on a 30-second interval that is about ten minutes, which the runner shortens by taking its warmup samples in a fast burst at startup.

The practical consequence: if you restart a runner while an endpoint is already misbehaving, the new baseline learns the broken payload as normal. Baselines live in memory only and are never persisted, so this is a real operational footgun rather than a theoretical one.

Step five: from a score to a signal

A score on its own is not an alert. Every passing check produces one, and the great majority are noise around zero. Three gates stand between the number and anything happening, and one of them also decides whether the baseline learns from this check at all.

The debounce

consecutiveBreaches is why one odd response is not a page. The counter increments on every breach and resets to zero the moment a check comes back under the threshold, so the signal requires N breaches in a row. At the default of 2 on a 30-second interval, a genuine change is reported within about a minute, while a single strange response is absorbed and forgotten.

The sampling valve

sampleEvery scores only every Nth passing check. Drift moves over hours, so coarse sampling costs very little resolution — it exists as the pressure valve if the hot path ever becomes CPU-bound. At sampleEvery: 10 you do a tenth of the embedding work and find out about a change in ten intervals instead of one. Left at 1 by default, because potion is cheap enough that most clusters never need it.

What the signal becomes

Once it fires, the runner ships an observation carrying the probe name and the score — and nothing derived from the body. The engine turns that into a single-member incident tagged bodyDrift, and the policy's actions run against it: a Prometheus gauge and a Kubernetes Event at minimum, plus whatever else the policy declares. The canary's status.phase stays Healthy throughout, because the check genuinely is passing — the drift shows up in status.intelligence instead.

Step six: one operation, three jobs

Cosine is doing all the work in all three model-driven triggers. What changes is what gets compared to what, and — the part that trips people up — which direction the comparison runs:

TriggerComparesMeasureFires whenSo that you learn
bodyDrift this body ↔ this probe's baseline distance distance > 0.15
far from normal is bad		 this endpoint is returning something it does not normally return, while still passing
failureCorrelation probe A's failure ↔ probe B's failure similarity similarity ≥ 0.85
close together means same cause		 these separate red checks are one outage, and which one to go and fix
failureNovelty this failure ↔ every known cluster similarity no cluster ≥ 0.80
close to nothing means it is new		 whether this deserves a fresh investigation or is the failure you already know about

So a rising number is bad for drift and good for correlation. They are the same underlying quantity — distance = 1 − similarity — pointed in opposite directions because the questions are opposite. Worth keeping straight when you tune thresholds.

Novelty clustering, concretely

There is no training step and no clustering algorithm in the usual sense. Each failure vector is compared against the centroid of every failure shape seen so far:

# for each new failure vector v best = the cluster whose centroid has the highest similarity to v if similarity(best, v) ≥ 0.80: known shape → count++, nudge that centroid toward v else: new shape → create a cluster with v as its centroid

A "cluster" is just a centroid, a count, and a first-seen time. Nudging the centroid is the same weighted average as the drift baseline, so a cluster tracks the family of failures it represents rather than only its first example.

Why the two models' vectors can never be compared

potion produces 512 numbers; MiniLM produces 384. Different lengths make the arithmetic impossible, but that is the shallow reason. The real one is that the axes mean different things. Each model arranged meaning into its own coordinate system during training, so position 12 in one has no relationship to position 12 in the other. Even if both produced 512 numbers, a cosine between them would be a plausible-looking number that means nothing at all.

Pulse tags every vector with its space and treats mixing them as a programming error — a panic, not a returned score — precisely because the failure would otherwise be silent and the corrupted numbers would look perfectly reasonable.

Vocabulary

embedding / vector
A fixed-length list of numbers standing in for a piece of text, arranged so similar meanings land near each other.
dimensions
How many numbers are in that list — 512 for potion, 384 for MiniLM. A property of the model, not a quality setting.
normalising (to unit length)
Scaling a vector so its length is exactly 1, keeping direction and discarding magnitude.
cosine similarity
How closely two vectors point the same way. 1 = identical direction, 0 = unrelated, −1 = opposite.
cosine distance
1 − similarity. 0 = identical, 1 = unrelated. This is what a drift score is.
centroid
The average of a group of vectors — the group's "middle" direction. Both the drift baseline and each novelty cluster are centroids.
mean pooling
Turning a variable number of token vectors into one document vector by averaging them.
EWMA
Exponentially weighted moving average — a running average that weights recent samples more heavily.
embedding space
The coordinate system one model produces. Vectors from different spaces are not comparable.

Moving parts

Two outbound streams, not one

It is worth being precise about which component talks to your observability stack, because they do very different things.

From the runnersFrom the engine
Granularityone record per checkone record per incident
Volumehundreds/sec at a few thousand canariesa handful per day
TransportPrometheus scrape; stdout JSON picked up by a node log agentdirect HTTP push from the action
Configured byHttpCanary.spec.outputsAnomalyPolicy.spec.actions
Carriesstatus, duration, drift score, latency z-scoreroot cause, members, novelty, the LLM analysis

The per-check stream is the one that predates this work — spec.outputs already chose between prometheus and stdout, and the drift and latency scores simply joined the metrics already there. Nothing about that changed.

spec:
  outputs:
    - {type: prometheus}   # /metrics on each runner — scraped
    - {type: stdout}       # one JSON line per check — for a Datadog/Fluent Bit daemonset

What is new is the second stream. An observability action pushes a fully-formed incident — root cause, affected checks, whether the failure shape was novel, and the investigation if an llm action ran first — straight to the backend, shaped per provider. That is a different kind of record than a check result, which is why it does not go through spec.outputs.

Sending both to Datadog is a reasonable setup, and they are not redundant. The runner stream gives you dashboards and alerting on raw check behaviour, at full resolution. The engine stream gives you one high-signal event per incident, already correlated and root-caused. Alerting on the first and reading the second is the intended shape.

Two models, two flows

This is the part worth internalising. The two models are not interchangeable, and the difference is not really about quality — it is about where in the pipeline text becomes a vector, and that placement is forced by two very different sets of constraints.

Start with the volumes

Drift scores every passing check. Correlation only ever sees failures. At any reasonable availability those differ by three orders of magnitude:

Canaries @ 30sPassing checks/sec hotFailures/sec cold
1,000~33~0.03
5,000~167~0.17
10,000~333~0.33

A transformer on the hot path would burn two to four cores continuously to track a signal that moves over hours. That is true of any transformer, so swapping MiniLM for something smaller does not rescue it.

The hot path: vectorise locally, ship a number

potion-base-32M is a Model2Vec static embedding. There is no transformer forward pass at all — inference is a token lookup and a mean over a baked matrix. Two consequences:

It is effectively free

Benchmarked at ~12,400 embeddings/sec/core on a 2.5 KB body — about 37× the 333/sec you would need at ten thousand canaries. A cache in front absorbs the common case where an endpoint returns a byte-identical body every check.

It needs no cgo

It is a []float32 matrix and a tokenizer, both pure Go. That is why the probe runner — the component that scales to N replicas — keeps its CGO_ENABLED=0 distroless/static image.

Because it is cheap and cgo-free, the model can live inside every probe runner. And because it lives there, the response body never has to go anywhere.

The cold path: ship text, vectorise centrally

all-MiniLM-L6-v2 is a real transformer, run through ONNX Runtime. It is slower and needs cgo and a shared library — but it only runs on failures, so the cost is paid once per outage rather than once per check.

More importantly, correlation cannot be done locally. Runners shard by probe name, so two canaries hitting the same broken backend almost always land on different replicas. A runner comparing failures only against its own slice would systematically miss exactly the incidents correlation exists to catch. The comparison has to happen where every shard's failures meet — which is the engine.

Vectors from the two models are never comparable. They occupy different embedding spaces, and a cosine distance between them would be a plausible-looking number that means nothing. The code treats mixing them as a panic-level wiring error rather than returning a score.

The same reasoning makes the cold model cluster-wide, not per-policy: correlation compares failures across policies, so per-policy models would make that either silently wrong or impossible. If policies disagree, the engine picks one deterministically and logs the ones it ignored.

Why bodies never leave the runner

This falls out of the placement rather than being bolted on. Because the body is vectorised in-process, the observation shipped to the engine for a drift signal carries no text at all — just the probe name, the score, and a fixed human-readable message. There is nothing to leak.

Failure text does travel, but it is normalised and redacted first: timestamps, UUIDs, IPs, durations and request IDs are masked, and any regex you list in triggers.bodyDrift.redact is stripped before anything is embedded or logged. The body is also excluded from /results and from CR status, and never appears in a language model prompt.

One more consequence: masking is load-bearing

Both paths normalise first, and it is not cosmetic. Real failure text is full of tokens that change every request. Left alone, every observation is unique — novelty reports everything as new and correlation never finds two failures similar enough to merge. Masking is what makes "have we seen this before?" answerable at all.

# before
dial tcp 10.96.0.5:5432: i/o timeout after 1.523s (req 3f2504e0-4f89-11d3-9a0c-0305e82c3301)

# after — and the same line an hour later normalises identically
dial tcp <ip>: i/o timeout after <dur> (req <uuid>)

Status codes are deliberately not masked. They are low-cardinality and meaningful — "everything is 503" and "everything is 404" are different incidents.

Deploying it

All of this has been run end to end on kind. Commands below use CONTAINER_TOOL=podman because that is what is on your machine; drop it if you switch to Docker.

  1. Fetch and convert the models

    Downloads potion and MiniLM and converts potion's safetensors into the flat binary the Go loader reads. About 210 MB, written to hack/models/, which is gitignored.

    make fetch-models

  2. Build the three images

    The engine image is the only one with cgo and ONNX Runtime; the other two stay CGO_ENABLED=0 on distroless/static.

    make docker-build              CONTAINER_TOOL=podman IMG=pulse-controller:v1
make docker-build-proberunner  CONTAINER_TOOL=podman PROBE_RUNNER_IMG=pulse-probe-runner:v1
make docker-build-incidentengine CONTAINER_TOOL=podman INCIDENT_ENGINE_IMG=pulse-incident-engine:v1

    Push them to wherever your cluster pulls from, then use those fully-qualified names below.

  3. Install the CRDs

    Three of them now: httpcanaries, grpccanaries, and the new anomalypolicies.

    make install

  4. Deploy the operator

    The controller creates the probe runner and, on demand, the incident engine — so it needs to know both image names.

    make deploy \
  IMG=ghcr.io/bryanbarton525/pulse-controller:v1 \
  PROBE_RUNNER_IMAGE=ghcr.io/bryanbarton525/pulse-probe-runner:v1 \
  INCIDENT_ENGINE_IMAGE=ghcr.io/bryanbarton525/pulse-incident-engine:v1

    At this point you should see the controller and a single pulse-probe-runner-0. No incident engine yet — that is correct, nothing has opted in.

  5. Confirm the models loaded

    Worth doing once per environment, because a model that fails to load degrades quietly rather than crashing.

    kubectl -n pulse-system logs pulse-probe-runner-0 | grep "body-drift model"
# Loaded the body-drift model {"model": "/models/potion/model.bin", "dimensions": 512}

If you are on Apple Silicon under podman/libkrun, the ONNX Runtime version matters more than you would expect. The wrapper is pinned to onnxruntime_go v1.21.0 against runtime 1.22.0 because they share C API version 22. Runtime 1.29 segfaults during environment creation on that CPU — its cpuinfo reports an unknown vendor. If you ever bump the wrapper, re-check ORT_API_VERSION in its header and move the ARG in Dockerfile.incidentengine with it.

Using it

The smallest thing that works

No credentials, no external services. Correlation plus a Prometheus metric and a Kubernetes Event:

apiVersion: canary.iambarton.com/v1alpha1
kind: AnomalyPolicy
metadata: {name: basic-triage, namespace: pulse-system}
spec:
  triggers:
    failureCorrelation: {}   # empty block = enabled with defaults
  actions:
    - {name: local, type: metric}

Then opt a canary in. Everything about the check itself is unchanged:

spec:
  url: https://payments.example.com/api/orders
  interval: 30
  expectedStatus: 200
  intelligence:
    policyRef: {name: basic-triage, namespace: pulse-system}

The engine appears within a reconcile. Delete the intelligence block from the last canary and it disappears again.

A realistic policy

spec:
  triggers:
    bodyDrift:
      enabled: true
      threshold: "0.15"          # cosine distance; see Operating notes
      warmupChecks: 20           # samples before scoring is trusted
      consecutiveBreaches: 2     # debounce — one odd response is not an alert
      redact:
        - "\"email\"\\s*:\\s*\"[^\"]*\""
    failureCorrelation: {enabled: true, windowSeconds: 120}
    failureNovelty: {enabled: true}

  topology:
    dependsOn:
      - {canary: default/payments-api, upstream: [data/postgres-health]}
    inferDependencies: true   # proposes edges; never acts on them

  actions:                      # fire IN ORDER for the root cause's policy
    - {name: local, type: metric}
    - name: investigate
      type: llm
      llm:
        endpoint: http://sglang-gateway.ai.svc:8000/v1/chat/completions
        model: gemma-3-27b-it
        apiKeySecretRef: {name: sglang-auth, key: token}
    - name: notify
      type: slack
      slack:
        webhookSecretRef: {name: slack-auth, key: webhook-url}
        includeInvestigation: true   # picks up the llm output above

Action order is meaningful: the llm action populates the analysis that the later slack action includes. One investigation per incident, not per canary — that is the whole point of correlating first.

On your SGLang deployment. A single SGLang instance is either generative or an embedder, never both. Your Gemma server is the llm action target; it will reject /v1/embeddings unless launched with --is-embedding. You do not need an embedding service — both models are baked into the images.

Operating notes

The drift threshold is measured, not guessed

Against a JSON payload whose item count, field values and timestamps all vary between checks:

ConditionDrift score
healthy variation — median0.015
healthy variation — p950.052
healthy variation — max0.063
empty result set0.200
truncated JSON0.204
null collection0.286
stack trace inside a 2000.473
maintenance page0.591

The default of 0.15 sits 2.4× above the worst healthy check and below the weakest real failure — a 3.3× gap, pinned by a regression test so a change to normalisation or the bundled model cannot quietly invalidate it. Raise it if your payloads vary more than that; lower it only with consecutiveBreaches raised to match.

Baselines are in memory, and that is deliberate

Nothing derived from a response body is ever persisted. The cost is that a rollout or a reshard blinds drift detection for one warmup period, which the runner front-loads by taking its warmup samples in a burst. A practical consequence worth knowing: if you restart the runner while an endpoint is already misbehaving, the new baseline learns the broken payload as normal.

Scaling out

Probes partition across replicas by a stable hash. One replica is the default and reproduces the original single-pod behaviour exactly.

kubectl -n pulse-system set env deployment/pulse-controller-manager \
  PULSE_PROBE_RUNNER_SHARDS=3

Status stays complete either way — with an engine the controller reads its aggregated view, and without one it fans out across the runners' own pod DNS.

Upgrading from a previous release

The probe runner became a StatefulSet but kept its name. The controller removes the old Deployment on first reconcile — this is handled, but it is the one part of the change that touches a running workload, so watch the first rollout. A Deployment of the same name that does not carry Pulse's labels is deliberately left alone.

Known rough edges

  • make lint is broken and was before this change: golangci-lint v2.8.0 cannot parse Go 1.27's export data. Fixing it means bumping GOLANGCI_LINT_VERSION. go vet passes.
  • Multi-arch docker-buildx targets have not been exercised — only native arm64.
  • The engine is a single replica holding in-memory state. A restart loses open incidents and novelty clusters; the settling period covers the resulting burst.
  • No load testing. The 12,400/sec figure is a Go benchmark, not a cluster measurement.
